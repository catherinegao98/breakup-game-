# 情侣分手指南 · 六人朋友局 v2

为 `catherinegao98/breakup-game-` 准备的 GitHub Pages 网站。六名玩家、一人兼任 DM；爆料和惩罚使用你确认的豆包自定义内容，其余图片来自你提供的 PDF。

## 先看清楚现在的状态

- 网站代码和卡牌图片已准备好，config.js 已填入你提供的 game-e194e 项目配置和数据库地址；尚未代你上传 GitHub。
- Firebase 控制台中的匿名登录、授权域名及数据库规则仍需你按下文确认完成；真实联机尚未验证。
- 未配置 Firebase 时，首页「打开单机演示」可完整体验页面。演示不联机、不保留进度。
- 联机版采用 Firebase 匿名登录 + Realtime Database + DM 浏览器处理请求，不需要自建服务器，不使用付费 Cloud Functions。
- DM 正常页面不显示其他人的手牌或隐藏礼物。房主拥有底层数据权限，技术上仍可检查这些内容，适合互相信任的朋友。
- DM 必须保持页面开启、网络在线；建议电脑或平板主持。手机锁屏、浏览器进入后台可能暂停处理，恢复页面后继续。
- v2 已加入美德／航行的私密发牌、出牌、摸牌和弃牌，以及船位与暗牌路线。表演、猜拳和卡效中的选择仍在线下完成，DM 根据牌面裁定并在控台提交实际牌张或位置变化。

## 第一步：创建 Firebase 项目

1. 打开 <https://console.firebase.google.com/>，登录你的 Google 账号。
2. 创建项目，例如 `breakup-game`；Google Analytics 可以不开启。
3. 本项目按免费 Spark 方案设计，不需要为此启用按量计费。免费额度仍有限，请以控制台 Usage/用量页面为准。
4. 项目主页添加 Web 应用（`</>` 图标），应用名任意。不必开启 Firebase Hosting，因为网站将放在 GitHub Pages。
5. 注册后复制 `firebaseConfig` 对象。

## 第二步：启用匿名登录

1. 左侧 Build / 构建 → Authentication。
2. 点击 Get started / 开始使用。
3. Sign-in method / 登录方式 → Anonymous / 匿名 → Enable / 启用 → 保存。
4. 在 Authentication → Settings / 设置 → Authorized domains / 授权域名中添加：

   ```text
   catherinegao98.github.io
   ```

5. 如果要本机开发，再添加 `localhost`；不需要把仓库名或 `https://` 填进域名字段。

匿名身份保存在当前浏览器。同一台设备上的不同浏览器，是不同玩家；同一浏览器的多个普通标签页，共用同一身份。

## 第三步：创建数据库，并发布权限规则

1. 左侧 Build / 构建 → Realtime Database → Create database / 创建数据库。
2. 选择可用区域，先使用 **Locked mode / 锁定模式**。
3. 创建后复制数据库 URL；它可能是 `https://某名称-default-rtdb.firebaseio.com`，也可能包含地区域名。请复制你自己的实际地址。
4. 数据库 → Rules / 规则。
5. 用文本编辑器打开本上传包中的 `database.rules.json`，复制完整内容，替换控制台里的规则。
6. 点击 Publish / 发布。

**不要用 `.read: true`、`.write: true` 的公开测试规则替代。** 本包规则使普通玩家无法直接读别人私牌、写分数或重置房间。玩家只能在空闲座位入座，并向 DM 提交自己的操作请求。

房间号相当于邀请凭证，分享给本局朋友即可。知道房间号并完成匿名登录的人可以看到公共状态；私密手牌仍按用户 ID 限制读取。

## 第四步：填写 config.js

用记事本或代码编辑器打开 `config.js`。保留 `export const firebaseConfig =`，把值换成刚才复制的配置。示例仅展示结构：

```js
export const firebaseConfig = {
  apiKey: "从控制台复制",
  authDomain: "你的项目.firebaseapp.com",
  databaseURL: "你在 Realtime Database 中复制的真实地址",
  projectId: "你的项目ID",
  appId: "从控制台复制"
};
```

如果控制台的配置没有 `databaseURL`，手动加上。也可以保留控制台提供的 `storageBucket`、`messagingSenderId` 等额外字段。

这个 Web 配置会随网页公开，属于预期行为；访问控制靠数据库规则。**不要放入服务账户 JSON、私钥、密码、GitHub token。**

## 第五步：上传你的 GitHub 仓库

仓库：<https://github.com/catherinegao98/breakup-game->，当前默认分支为 `main`。

1. 解压上传包，进入 `breakup-game` 文件夹。
2. 登录 GitHub，打开上面的仓库。
3. 点击 Add file → Upload files。
4. 先上传根目录文件：`index.html`、`style.css`、`app.js`、`engine.js`、`rounds.js`、`round-ui.js`、`decks.js`、`cards.js`、`assets.js`、**填好配置的 `config.js`**、`database.rules.json`、`package.json`、`README.md`。README 可替换仓库中原先只有标题的版本。
5. 页面底部点击 Commit changes，提交到 `main`。
6. 再次 Add file → Upload files，把整个 **`assets` 文件夹**拖入，确认路径是 `assets/文件名.jpg`，再 Commit changes。这里有88张图片，单独这一批小于100个文件。
7. 再次上传整个 **`rule-images` 文件夹**，确认路径是 `rule-images/文件名.jpg`，提交。这里有14张规则图片。
8. `tests` 文件夹可以一并上传用于保留测试；它不是运行网站的必要文件。
9. `.nojekyll` 是隐藏文件，可用 Add file → Create new file，新文件名填 `.nojekyll`，内容留空并提交；无法提交空内容时可填一行 `# static site`。

**必须把文件放在仓库根目录，而不是再套一层 `breakup-game/` 文件夹。也不要只上传 ZIP，GitHub Pages 不会自动解压它。**

## 第六步：开启 GitHub Pages

1. 仓库 → Settings → 左侧 Pages。
2. Build and deployment → Source 选择 **Deploy from a branch**。
3. Branch 选择 **main**，目录选择 **/(root)**。
4. 点击 Save。
5. 等待 Actions 中 Pages 部署成功，再打开：

   <https://catherinegao98.github.io/breakup-game-/>

这是预计发布地址；只有你完成上传和 Pages 部署后才会有网站。注意末尾仓库名中的短横线。

## 本局牌堆与分级依据

用户授权按影响范围与控制力分为轻／中／重，每种效果分别放3／2／1张。这是**朋友局自定义权重**，不是原手册明确列出的配比；轻重指影响强度，并不表示一定是坏效果。

### 航行事件：15张，三条路线各5格

| 原卡效果 | 分级 | 张数 | 本局分级依据 |
| --- | --- | --- | --- |
| 激流 | 轻 | 3 | 单次骰点推进一艘船 |
| 漩涡 | 中 | 2 | 互换两艘船的位置，改变竞争格局 |
| 补给 | 轻 | 3 | 摸牌或弃牌类资源变化 |
| 交换 | 重 | 1 | 可以让船上／落水玩家互换，直接改变存活与座位 |
| 物资 | 轻 | 3 | 三张行动牌的分配 |
| 拯救 | 轻 | 3 | 一次指定玩家的猜拳救援 |

每个格子是独立事件牌实例；即使图片相同，也可以在不同位置出现。只有船走到该格时才公开，尚未翻开的顺序不向普通玩家下发。

| 原卡效果 | 分级 | 张数 |

| 榜一大哥 | 轻 | 3 |

分级大致按单人资源／帮助、位置或落水变化、群体效果／强力抵消区分。每张牌有独立编号，重复图片不等于重复使用同一张牌。「举起双手」「好大的浪」的整场限一次仍保留。

牌堆空时，DM 可以洗回已弃的牌。**若牌堆与弃牌均空，手册未明确如何处理**，网站不会偷偷生成牌；DM 可明确裁定本回合跳过摸牌，操作会写入日志。没有需要摸的牌时，也可先按公开牌效或已有手牌继续裁定，不伪装成原规则。

### 紫色礼物行动：每轮6张，共两轮

| 行动编号 | 牌名 | 使用方式 |
| --- | --- | --- |
| 1、2 | 偷窥 | 私下查看任意两名不同玩家的礼物 |
| 3、4 | 交换 | 交换任意两名不同玩家的礼物 |
| 5、6 | 翻转 | 翻转任意一名玩家的礼物好坏 |

紫色牌采用文字卡面，与航行牌堆独立。每轮六人各随机获得一张，数字决定行动顺序；每人只看到自己的牌，已使用的牌保留作记录。到行动编号时，才公开执行者与效果；其他人尚未执行的牌和整轮顺序不直接公开。偷窥内容只有执行者收到，礼物本身继续隐藏。

### 美德：78张

六种基础颜色，每种数字1—6、每张两份，共72张；善变的三种规则效果各两份，共6张。每个实例有独立ID。现有扫描图只提供一种善变卡面，另外两种按手册以文字牌展示，不冒充原图。

## 新版开局与各阶段操作

1. 兼任 DM 创建房间并选择角色，复制邀请链接给另外五人。六人均入座后再推进。
2. 节目开场：按线下剧本完成开场，暂不开放后续游戏牌。
3. 观众来电：六张来电随机私发，每人一张；持牌玩家按编号1—6依次公开。被提到的人先介绍再解释；DM 点「本条分享完成，下一条」。
4. 爆料：沿用之前的私密发牌、相信／质疑、私下查看和传递；使用豆包自定义18张爆料和12张惩罚。
5. 吵架与评分：DM 可发放本人角色的三张心声辅助卡。心声的具体发放时机未在现有手册段落找到明确指令，因此保留为本阶段主持开关，不擅自随机分给其他角色。
6. 评分：每人1—4分各使用一次，给自己和 CP 以外四人评分。提交的分值仅本人可见，六人共24份评分完成后 DM 揭晓。队伍排名、并列以及对应恩爱值由 DM 按手册裁定并在记分控台记录。
7. 美德：进入阶段时自动洗牌，六人各得6张私密手牌，随机决定首位。选择1—5张自己的牌出牌，系统校验同色／同数字／顺子；顺子必须执行最大数字牌的效果。
8. 美德牌效：玩家按卡面决定选择或目标，DM 在「美德牌效控台」提交摸牌、两人全手牌交换、从他人手中暗抽1张。需要玩家展示或弃牌时，DM 发出请求，由玩家本人在手牌中选择，不能代为查看。
9. 慷慨：DM 逐张翻牌，翻牌公开显示；可勾选分配给玩家。同色出现时必须全部给出牌者，六色成功分配后清空出牌者手牌。牌效完全结算后，DM 确认结束回合，再判断是否打光。
10. 美德胜利：一次打光记队伍一次胜利并 -5，第一次补4张。任一队累计两次打光，或6轮结束，结束阶段。剩余手牌结算由 DM 根据原手册记录。体贴可授予额外回合，额外回合不能再次使用体贴。
11. 礼物：六人礼物隐藏；第一轮随机私发六张紫色行动，依次执行。第二轮重新私发。十二次行动完成后，DM 揭晓礼物并结算一次；双好 +15，双坏 -15，一好一坏0。
12. 航行：默认按上表配置15张事件与20张行动，DM 可在开局或礼物阶段调整配比。每人初始3张行动牌，六人按恩爱值次序选择船；DM 可在第一人登船前确认同队／并列先后顺序。快艇1人、帆船2人、游轮3人。
13. 航行回合：当前玩家先摸1张、再出牌、主动结束回合。超过4张必须由本人选择弃到4张；任何时候可用的牌仍受具体牌面条件限制，DM 裁定。注意安全可以响应哎呀脚滑；装疯卖傻的抵消由 DM 明确确认。
14. 六人完成回合后，DM 按快艇→帆船→游轮推进有人的船。每次前进翻开相应的事件；DM 处理表演、猜拳、船位与落水、资源变化后，确认结算。事件引发额外前进时，新增事件进入待处理队列。
15. 漩涡可以使用专门控件互换船位置，原领队移至队尾；其他位置／落水变化在六人的船位表中提交，系统限制船容量，并保留原船队顺序、新上船者排末尾。
16. 三艘船本轮推进完后再进行本轮结算，网站按领先有人船计算每名船员 +10／并列两艘 +5／三艘并列0，累计到各自队伍。落水者动作在线下执行。第一艘有人船驶出路线，船上每名玩家 +30并结束。
17. 进入分手仪式，按最终恩爱值及手册处理结局；并列由 DM 裁定。

## 正常玩家能看到什么

- 只收到本人的爆料、美德手牌、航行行动牌、紫色礼物行动牌、心声、评分及偷窥结果。
- 观众来电先本人持有，再按编号公开。
- 公共页面只显示已打出的牌、明确展示的牌、已翻开的事件、公开分数和牌张数量。
- 「当前规则」只给当前阶段说明，不再列出完整未来卡牌库。
- 私牌不能依靠隐藏按钮保护：普通玩家订阅公共状态和自己的私密分支，数据库规则限制读取他人分支。
- 静态卡面图片和效果定义本身可从网站文件访问，真正隐藏的是牌堆顺序和牌归属。此版不对房主提供防作弊保证。

## 刷新、断线和换人

- 同一浏览器资料中的匿名登录身份会保留；刷新或重新输入房间号可恢复原角色。不要清除站点数据，勿在关闭无痕窗口后期待恢复。
- DM 保持页面开启；掉线后暂停操作，回到原浏览器同一房间后继续处理。没有第二位DM自动接管。
- 换一批人、身份丢失或从旧版升级，建议创建新房间。重置会清空进度，但保留座位。
- 旧房间需要手动清理时，在 Firebase 数据页确认房间号后删除对应记录；代码不自动删除数据。

## 验证与边界

- 26项核心逻辑测试已通过，覆盖发牌数量与唯一实例、私密投影、回合／阶段权限、出牌组合、弃牌与展示、礼物两轮和一次结算、请求重放与重置、航行容量、响应牌以及终点结束。
- 浏览器演示已走通观众来电六张按序公开、六人24份评分、美德私密六张手牌与慷慨翻牌分配，以及原有礼物两轮流程；航行暗牌路线与私密行动牌界面已检查。
- 新增紫色牌的私发与跨轮更换已在浏览器演示实际检查，并有独立逻辑测试。真实 Firebase 六台设备联机，以及规则模拟器未验证，正式开局前需六台设备实测。
- 系统不自动理解表演、猜拳或玩家口头的自愿选择。DM 按已公开牌面裁定并在控台提交状态；控台提供的是牌效操作工具，不宣称自动执行所有特殊条件。
- 手册没有明确写出的弃牌重洗／摸空牌堆，由 DM 明确裁定并记录，不偷偷补牌。

正式局前检查：两人同时选同一角色只能一人成功；各自只见本人手牌；新规则发布后新操作不报权限错误；DM断线恢复；重复提交不能重复结算；六人刷新后状态一致。
